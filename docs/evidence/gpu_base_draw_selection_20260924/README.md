# GPU base draw-selection diagnosis (2026-09-24)

The GPU candidate is not ready for performance tuning. Its native processing state can report an LOD0 chunk as `visible` while the renderer does not select any LOD0 terrain draw. The base-coverage cut selects an active LOD3 root before considering its descendants (`wt_terrain_gpu_base_coverage.gd::_cover`). A complete LOD3 root therefore hides all finer active chunks within it.

To distinguish processing from presentation, the renderer now reports `selected_terrain_lod_counts` alongside `active_terrain_lod_counts`. The bounded `base_coverage_edit_probe` prints both per sample. This instrumentation changes no draw or collision behavior.

Reproduction: `python tools/probe_gpu_base_startup.py --godot 'C:\Program Files (x86)\Steam\steamapps\common\Godot Engine\godot.windows.opt.tools.64.exe' --seconds 12 --memory-gib 3 --mode base_coverage_edit_probe` on game commit `62daa32` plus this diagnostic. Probe exited 0 in 9.82 s; peak RSS was 741 MiB. At frame 20 / 499 ms after edit, 10 LOD0 and 13 LOD3 chunks were active, but the selected terrain counts were only 13 LOD3. At frame 44 / 1235 ms, 10 LOD0 chunks remained active, but the selected terrain counts were only 20 LOD3. The local native processing state called LOD0 `visible` at both times. The output is in `.godot/world_transvoxel_captures/base_coverage_probe/godot.log`.

This is a presentation correctness failure. The draw cut must be rebuilt as an atomic, complete, balanced mixed-LOD cover over the loaded base. For a selected child, the corresponding parent regular brick must be suppressed in the same publication; all uncovered parent bricks and required transition geometry must remain drawn. Failed or incomplete child groups must leave their old cover intact. A test must assert actual selected draw counts and geometry/revision at the edited point; native `visible` state alone is not an acceptance criterion. Only after that gate passes should edit latency, streaming throughput, or wattage be optimized.
